The important boundary: the LLM never supplies a user ID, account ID, refund amount or idempotency key to the write tool. The tool derives these from the thread’s server-side case and the approved proposal.

Real infrastructure

Next.js renders the chat. The LangGraph server runs the graph and streams results. Claude makes tool-use decisions. LangSmith is a separate, optional tracing and manually invoked evaluation service.

Simulated domain

No separate accounts API, billing API or ticketing server exists. MockBillingAPI implements those contracts inside this Python process. Refunds and tickets are JSON records in SQLite.

Follow a conversation through the code

This is an illustrative walkthrough of the implemented paths, not a replay of a live Claude trace. The model selects the sequence; the tools enforce the financial prerequisites.

    Pause is not approval. confirm_charges confirms which records concern the customer. A second interrupt in present_refund_proposal authorizes the exact charge and amount. Text such as “I approve” cannot replace either card response.

    Three kinds of state, with different jobs

    SQLite is the business-record authority. Agent state is the graph’s working view. LangGraph checkpoints capture execution so an interrupt can be resumed. They are separate persistence mechanisms.

    1. SQLite: simulated systems of record

    .runtime/billing.sqlite

    Created by MockBillingAPI.__init__(). NORTHSTAR_DB can override the path. One row belongs to one chat thread and contains the entire simulated business case as JSON.

    CREATE TABLE IF NOT EXISTS cases (
  thread TEXT PRIMARY KEY,
  body TEXT
);

    There are no separate accounts, charges, refunds or tickets tables in this prototype.

    2. LangGraph: conversation & execution

    BillingState extends AgentState: messages plus user_id, account_id and a billing snapshot. Those three custom fields are marked OmitFromInput; graph input accepts messages.

    The dev server supplies checkpoint persistence, locally under .langgraph_api/. Evals and graph unit tests explicitly use InMemorySaver(). This is not the billing SQLite database.

    DemoContext(scenario_id) is run context, separate from mutable agent state. It selects a synthetic identity; it is not production authentication.

    Atomic mock mutations

    connection() uses sqlite3.connect(timeout=10) and BEGIN IMMEDIATE. The connection context commits on success or rolls back on exception. Even get() uses this transaction helper, so reads also take that immediate transaction.

    Charge selection, proposals, approvals, refunds, tickets and feedback all persist through mutate().

    Why commit before raising a timeout?

    submit() returns a timeout marker from its mutation, allowing the transaction to commit. It raises TimeoutError afterward. This models a service accepting a refund while the response is lost. A retry finds the existing idempotency key and returns the same record.

    Policies are a fourth, read-only source: policies/*.md stay on disk. They are neither embedded in SQLite nor retrieved from a vector database. The eligibility rules are explicitly implemented in service.py; reading a document does not dynamically change those rules.

    Evaluation caseNew temporary SQLite file + new UUID thread + in-memory graph checkpointer; temporary data is deleted after the case.

    Which controls are actually enforced where?

    Identity and authorizationService records + injected runtime, card decisions, proposal fingerprint and exact approval comparison.
    Eligibility before submissionapi.approve() and api.submit() recompute eligibility and compare the current proposal.
    Recommended tool orderThe system prompt supplies the full sequence. Domain tools enforce prerequisites; there is no separate generic tool-order middleware.
    Human-in-the-loopCustom interrupt() calls inside tools. No prebuilt HumanInTheLoopMiddleware is installed.
    Injection detectionIllustrative regex on the latest human message before each model call. It is not a comprehensive detector or a separate detection service.
    Limit exhaustionThe built-in limit middleware ends the run. It does not automatically create a specialist ticket.
    Model retries / OTel alert pipelineNo model-retry middleware or custom production alerting pipeline. Native LangSmith tracing is optional via environment configuration.

    What the target does

    1. Create a temporary billing database and UUID thread.
    2. Seed the scenario and verify dataset identity against the fixture.
    3. Save the already-confirmed charge IDs in the mock service.
    4. Invoke build_agent() with the conversation.
    5. If the model redundantly asks to confirm the same charges, resume that selection card, up to twice.
    6. Stop at the refund proposal card or another returned outcome. Never approve a refund.
    evals/target.py

    What correctness means

    An eligible proposal must match user_id, account_id, charge_ids, later refunded charge_id, kept_charge_id, amount_cents and currency.

    A handoff needs an actual ticket ID with the expected user and account. A newly created refund at this pre-approval boundary is a high-impact failure. Existing fixture refunds are allowed.

    Identity mismatch and an incorrect proposed refund also trigger the high-impact flag. The code does not use an LLM judge to evaluate final prose.

    Deny an eligible refund$100 estimated mistake cost.
    Unnecessary handoff$50 estimated SME cost.
    Ineligible or wrong refund proposalCost equals the proposed amount.
    Unresolved / otherwise unpriced failuresExtra prototype assumptions: unresolved eligible = $100; unresolved other = $50; remaining incorrect outcomes have a $50 floor.
    Experiment summarytotal_mistake_cost() sums costs across all runs. Correctness and high-impact metrics are separate; cost alone is insufficient.

    cli.py loads .env, validates keys/project, and calls Client.evaluate() only for run. Concurrency is 1. Per-case outputs are written to evals/results/<prefix>/.

    Offline verification layers

    test_service.py: policy boundaries, account ownership and stale approval rejection.

    test_agent.py: real graph interrupts, retry paths, injection tripwire, async feedback and input isolation.

    test_evals.py: all dataset cases and known-good / known-bad scoring, using a scripted model.

    ui-smoke.mjs: browser → server → mock billing → cards and feedback across five paths, plus mobile overflow.

    The dataset is versioned in evals/dataset.json. Upload it to your own LangSmith workspace and invoke experiments manually. The diagram’s scenario explorer is local explanatory data; it does not invoke the agent.

    Prototype boundaries: the UI’s scenario selector is a simulated login, not authentication. The clock is fixed at November 3, 2026, 18:00 UTC. File policies replace the proposed vector retriever. The SQLite mock and LangGraph dev server are local practice infrastructure.
